Platform guidance

Mobile design guidance

Design for the task and available space first. Keep the Blue Horizon identity consistent while using platform conventions when building native Android and Apple apps.

Shared mobile principles

Use for responsive web and native experiences

All platforms
  • LAYOUTAdapt to the content width
    Stack related content into one column when space is limited. Let navigation, cards, and forms reflow instead of shrinking desktop layouts.
  • PRIORITYKeep the main task and next step visible
    Shorten supporting copy, preserve clear headings, and avoid fixed bars that cover content or the keyboard.
  • TARGETSMake touch controls comfortable and separated
    For the web version, use at least 44 × 44 CSS px for primary touch controls as this system’s baseline; increase where practical and prevent neighboring hit areas from overlapping.
  • CONTENTAllow text and controls to grow
    Support larger text, longer localized labels, wrapping, and portrait or landscape layouts without clipping.
  • DATAReformat dense information deliberately
    Prefer a concise result card on phones. If a table must remain tabular, give it a labeled horizontal scroll region and keep important context visible.

Platform references

Respect each platform’s own sizing units and interaction patterns

Native apps
  • MATERIALAndroid · Material Design
    Use adaptive layouts that change with available window space. Android’s accessibility guidance recommends interactive touch areas of at least 48 × 48 dp; dp is a density-independent Android unit, not a CSS pixel.
    Material 3 adaptive layout examples · Android touch target guidance
  • APPLEiOS and iPadOS · Human Interface Guidelines
    Apple recommends a 44 × 44 pt hit region for buttons. Respect system safe areas, adapt to orientation and window size, and support Dynamic Type so text and rows can expand without overlap.
    Apple button guidance · Apple layout guidance · Apple accessibility guidance
Keep units distinctCSS px, Android dp, and Apple pt are platform-specific units. Treat the values above as separate platform recommendations, not direct conversions. A shared visual system can align intent while native implementations use their platform’s units and controls.

Mobile review checklist

Review the complete flow at narrow and enlarged layouts

CheckTap every control with a finger; test keyboard and screen-reader navigation; enlarge text; rotate the device; check safe areas and on-screen keyboard; confirm focus, errors, and sticky elements never hide the current task.
AvoidRelying on hover, tiny icon-only actions, fixed-width content, unexplained swipe gestures, or a “mobile” layout that only scales down desktop UI.

How to use this system

Use the shared foundations first, then choose a documented component or pattern. If a case is missing, record the need and propose an extension instead of creating a one-off style.

01 · START

Use the tokens

Choose a semantic token such as action, surface, or feedback before reaching for a raw brand color.

02 · COMPOSE

Follow the pattern

Reuse the established order, responsive behavior, and content model for common member tasks.

03 · EXTEND

Share the exception

Document the user need, accessibility impact, and proposed reusable change with the system owner.

Content and layout conventions

Small choices that keep interfaces clear across products

PreferSentence case, short headings, explicit field labels, familiar healthcare terms, and dates written so the month is unambiguous.
AvoidColor-only instructions, unexplained abbreviations, placeholders used as labels, and forms that jump between columns on narrow screens.
Links are destinations; buttons are actionsVisited links use purple. Make link text describe its destination; avoid vague labels such as “Learn more.” Align form controls and actions to a common left edge, and keep the main action first in keyboard and reading order.

Interaction checklist

Required in every shipped flow

  • KEYBOARDAll controls are reachable and operable
    Keep a visible focus indicator; do not trap focus.
  • FORMSLabels and errors are programmatically connected
    Use persistent labels, `aria-describedby`, and `aria-invalid` when needed.
  • DIALOGFocus enters the dialog and returns to its trigger
    Provide a clear close action and support Escape.
  • STATUSMeaning is not conveyed by color alone
    Include text and a meaningful icon or shape.
  • ZOOMContent reflows at narrow widths and 200% zoom
    Tables may scroll horizontally inside a named region.
  • MOTIONRespect reduced-motion preferences
    Keep movement brief and nonessential.
11 · Experience patterns

Patterns

Patterns combine individual components into predictable journeys. These initial patterns are derived from the member and provider reference material.

Member sign-in

Keep the secure task focused and recoverable

Authentication
1Ask for the member ID
Keep the label visible; give a short hint about where to find it.
2Collect the password
Mask by default, provide an explicit show/hide control, and support password managers.
3Recover without blame
Place password recovery near sign-in and explain errors in plain language.

Provider search

Make results useful before they become dense

Search & results
1Set the search context
Ask for specialty and location with clear labels and accessible autocomplete behavior.
2Show useful filters
Keep the applied filter count and a clear way to remove filters visible.
3Present scannable results
Show provider name, specialty, location, distance, and network status; include empty and loading states.
Pattern library is a starting pointClaims, biometrics, account creation, and benefit-selection flows need product, clinical, privacy, and security review before their rules are considered standard.
